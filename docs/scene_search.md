# 方向の転換: 用途を「場面の時刻を当てる」に絞る

2026-10-14 の議論で決めた。経緯と決定事項、実装の定義をここにまとめる。

## 経緯

1. GRPO を 2 回回し、Perception Test（室内の演技映像）で学んだことが Japanese Video-QA（日本の YouTube 映像）に移らないことが確定した（`docs/grpo_run2.md`）
2. 日本の CC BY 動画から学習問題を作る試作で、順序・動作・位置の問題は作れたが、数を数える問題は作れなかった（235B でも数が安定しない。`docs/ja_data.md`）
3. 「一般的な映像モデルの学習の方が良いのでは」という問いに対し、予算（数千問）では使い道と同じ種類の映像に寄せるのが 1 問あたりの効果が最大、と整理した
4. さらに「用途を絞る」提案から、答えの種類を「存在・時刻・順序」→「時刻のみ」に絞った

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| モデルの仕事 | 映像と日本語の問いを受け、**問いが指す場面の時刻**を答える | ユーザーストーリー「〇〇が△△している場面を探せる」そのもの。temporal grounding と呼ばれる課題 |
| 作らないもの | 数を数える問題、存在（はい/いいえ）、順序の 4 択、自由記述 | 数は作れない。存在は実用性が薄い。順序は時刻の学習が効くかを 4 択 49 問で観察するだけにする |
| 出力の形 | 根拠 1〜2 行 + 最後の行「答え: 1:42」。上限 96 トークン | 1 トークンの答えでは手続きが学べず多様性もすぐ消える（GRPO 2 回の教訓） |
| 正解の判定 | 答えの時刻が正解区間 ± 許容幅に入れば正解。許容幅 = max(5 秒, フレーム間隔 / 2) | 32 フレームでは 20 分の動画で間隔 37 秒。フレームより細かい時刻は原理的に当てられない |
| 部分点 | 許容幅から外れた秒数 d で max(0, 1 − d / 30) | 報酬のばらつき（学習信号）を増やす |
| 評価 | (1) Japanese Video-QA 全 800 問の時刻正解率 (2) 自前 dev（日本の映像、動画単位で分離） (3) Perception Test dev 405 問（汎化の監視） (4) 4 択 220 問（壊れていないかの確認） | 本番・学習の進み・狭くなりすぎの 3 つを別々に見る |
| 学習データ | 日本の CC BY 動画 1,000 本から「場面の説明 + 時刻区間」を生成し、再特定の一致で検査 | 1 本 6 場面以上。順序の 4 択を作る工程が不要になる |
| 計算資源 | 評価・選別は Colab。10 時間を超える学習だけ AWS（`g6e.xlarge` L40S 48GB、スポット） | AWS は「ここぞ」のときだけ使う |
| 見送り | 海外の実世界映像との比較実験。`indx-proposal.md` の書き換え | 今回は日本の映像で結果を出すことを優先。方向転換は Artifact に書く |

## 評価の定義（`movie_llm/eval/timeloc.py`）

- 注釈の時刻表記は 6 種類。`00:01:00.000` のような表記は「時:分:秒」でなく「分:秒:フレーム」で書かれていることが 71 問あり、動画の長さと照らして判別する（`parse_time`）
- 正解区間の長さは中央値 5 秒、4 分の 3 が 13 秒以下
- モデル出力は「答え:」の行から `分:秒`、`N分M秒`、`N秒` を読む（`extract_time`）
- 当て推量の基準として「常に動画の中央と答える」正解率を併記する
- 採点: `scripts/jvqa_predict.py --task time` → `scripts/jvqa_eval_time.py`

2B・16 フレーム・8 問の動作確認では 1 / 7 正解。出力の形が崩れる（「答え: 分:秒」をそのまま書く）回答があったので、指示文に答えの例を入れた。4B・32 フレームの基準値は `notebooks/colab_timeloc_4b.ipynb` で測る。

## 成立条件と対策

- 学習前の 4B の正解率が低すぎる（10% 未満）と GRPO の学習信号が出ない。その場合は「0:00〜0:30 のどの区間か」の選択式から始め、途中で直接の時刻に移す段階づけにする
- 長い動画はフレーム間隔が粗い。製品では「粗く当ててから該当部分を細かく見る」2 段階にする（推論時の工夫、学習の範囲外）
